# NamToCloResearch

Focused Windows x64 research tool for converting Neural Amp Modeler (`.nam`) files to the VTSI/CLO representation produced by Hotone Ampero II's `HTUSBTools.dll`, and for comparing that result with Valeton GP-200 captures.

The repository does **not** redistribute proprietary Hotone or Valeton files.

## Current scope (v0.8.0)

The code was deliberately reduced after the earlier experiments.

### Kept

- `HTUSBTools.dll::namConvertCloData` only.
- Isolated worker process so a native DLL failure does not kill the parent CLI.
- Shared caller-owned `0x2288` output buffer.
- Normal Ampero VTSI generation: 2048-float Block B.
- Optional confirmed GP-200 compact serialization: keep Block A and the first 1024 Block-B floats, update header fields, zero trailing padding, recalculate CRC16/MODBUS.
- CLO inspection and GP-200 block comparison.
- Simple `runtime\ampero` layout.

### Removed

- Sonicake provider and `5868USB.dll` support.
- `cloConvertSampleRate` and cross-runtime matrices.
- Legacy `namConvertClo` file API.
- `--arg6` sweep; argument 6 is fixed to `0`.
- Experimental `2048 -> 1024` DSP patch.
- Experimental `44100 -> 48000` VTSI-stage patch.
- Probe/matrix scripts associated with those discarded hypotheses.

These were useful research steps, but are no longer part of the active investigation.

## Confirmed findings behind this cleanup

1. `namConvertCloData` can generate a complete `0x2288` VTSI outside the Ampero editor.
2. Ampero and Sonicake generated byte-identical VTSI for the tested NAM files.
3. `cloConvertSampleRate` changes coefficients but does not explain the Valeton/Ampero difference.
4. Valeton internally builds a 2048-coefficient VTSI and its GP-200 compact stage simply keeps the first 1024 Block-B floats. It does not recompute a 1024-coefficient fit.
5. Therefore the remaining investigation is upstream: why Valeton's 2048-coefficient identification result differs slightly from Ampero's.

## Build

Requirements: Windows x64, CMake 3.24+, Visual Studio 2022/2026 Build Tools with MSVC.

```powershell
cmake -S . -B build -A x64
cmake --build build --config Release --parallel
```

The GitHub Actions workflows build the same target on Windows.

## Runtime layout

Keep all proprietary runtime material outside Git:

```text
NamToClo.exe
runtime\
└─ ampero\
   ├─ HTUSBTools.dll
   └─ nam_input_wav.wav
```

`runtime\ampero` is discovered automatically relative to `NamToClo.exe`.

You may also use:

```powershell
NamToClo.exe model.nam output.clo --ampero-dir "C:\path\to\Ampero II"
```

or explicit `--dll` / `--stimulus` paths.

## Commands

Generate the normal Ampero 2048-coefficient VTSI:

```powershell
.\NamToClo.exe .\model.nam .\ampero-2048.clo
```

Generate the same normal fit and then serialize the confirmed GP-200 compact shape:

```powershell
.\NamToClo.exe .\model.nam .\gp200-compact.clo --gp200-compact
```

Inspect a CLO:

```powershell
.\NamToClo.exe --inspect .\ampero-2048.clo
```

Compare two CLO files, including Block A / Block B correlation and error metrics:

```powershell
.\NamToClo.exe --compare-gp200 .\ampero-2048.clo .\valeton-reference.clo
```

Check runtime discovery and required export:

```powershell
.\NamToClo.exe --check-runtime
```

Add `--verbose` only when native-call diagnostics are needed. Use `--keep-temp` to preserve the generated output WAV and captured shared buffer for reverse-engineering work.

## Active research target

The current target is **not** the CLO container or GP-200 compaction; those are understood well enough for the present work. The target is the identification stage that produces the 2048-float VTSI model before Valeton compacts it.

Keep confirmed observations separate from hypotheses when extending this repository.
